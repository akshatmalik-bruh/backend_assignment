INTENSIVE ARCHITECTURE DOCUMENTATION - CONTENT BROADCASTING SYSTEM

1. ARCHITECTURAL PATTERN: SEPARATION OF CONCERNS (SoC)
------------------------------------------------------
The system is built using a strict modular SCR (Service-Controller-Route) architecture:
- Routes: Define the entry points and apply specific middlewares (Auth, Multer).
- Controllers: Handle request parsing, validation (Zod), and HTTP response formatting.
- Services: Contain the pure business logic and interact with the database via Prisma.
Benefit: This decoupled design allows for independent testing of business logic without needing to mock HTTP requests, ensuring high maintainability.

2. AUTHENTICATION & RBAC (DEFENSE-IN-DEPTH)
-------------------------------------------
- Strategy: Stateless JWT authentication using the HS256 algorithm.
- Security Layers:
  a) Global Auth Middleware: Verifies token integrity and decodes the payload into `req.user`.
  b) Controller-Level RBAC: Immediate rejection of unauthorized roles (e.g., Teachers trying to access Principal endpoints).
  c) Service-Level Validation: A final check inside the business logic layer to prevent any potential middleware bypasses.
- Password Security: Industry-standard Bcrypt hashing with a cost factor (salt rounds) optimized for security vs. performance.

3. DETERMINISTIC SCHEDULING & ROTATION ENGINE
---------------------------------------------
This is the system's most complex component. Unlike a naive "random" picker, this uses a deterministic algorithm based on the Unix epoch.
- Mathematical Logic:
  1. Filter: Identify all content where [status=approved] AND [startTime <= current_time <= endTime].
  2. Group: Partition active items by 'subject'.
  3. Calculate Total Cycle: `TotalCycleTime = Σ(rotationDuration_i)`.
  4. Calculate Current Offset: `CurrentOffset = Date.now() % TotalCycleTime`.
  5. Selection: Iterate through the sorted list. If the CurrentOffset falls within the time-range of an item, that item is returned as "Live".
- Efficiency: O(n) time complexity where n is the number of active items per subject (typically very small). This avoids the need for heavy cron jobs or worker threads.

4. DATABASE DESIGN & DATA INTEGRITY
-----------------------------------
- ORM: Prisma 7 (using Driver Adapters for direct PG access via @prisma/adapter-pg).
- Connection Management: Implemented a Singleton pattern for the PrismaClient to prevent connection leaks (critical for serverless or containerized deployments like Render).
- Integrity: Used Prisma Enums for 'Role' and 'Status' to ensure data consistency at the database level.
- Relationships: Established a strong User-to-Content relation to track ownership and uploader accountability.

5. FILE MANAGEMENT & STATIC ASSET DELIVERY
------------------------------------------
- Strategy: Local Disk Storage using Multer.
- Security:
  - Filename Sanitization: Prefixed with `Date.now()` to prevent collisions.
  - MIME Filtering: Strict allow-list (JPG, PNG, GIF).
  - Buffer Protection: 10MB hard-limit on file size.
- Delivery: Served via `express.static`, allowing the server to handle file streaming without loading the entire asset into memory.

6. EDGE CASE HANDLING
---------------------
- Empty State: If no content is active/approved, the system returns a specific 200 response with a "No content available" message (not an error), as per the business requirements.
- Expired Content: The rotation engine automatically purges expired content from the "Live" view without requiring a manual update.
- Invalid Subjects: Subject filtering is implemented using optional Prisma where clauses, handling missing or misspelled subjects gracefully.
